# 周期卡顿诊断

基线为 v0.4.0-rc.simple.2 对应源码，仅加入本地诊断埋点；原刷新/存储行为未修改。基线程序及其源码差异保存在 artifacts/v04-polish/baseline-build 与 instrumentation-only.diff。后续原始事件分别在 perf-before、perf-after、perf-final，最终发布程序的完整对比另见验证报告。

同一合成场景：300条历史记录、395个参考节点、1200×800、192DPI、默认渲染配置；自由计时125秒，依次今日、展开知识树、学习数据；30秒左右暂停300ms后继续。测量期间不写性能日志，结束后才输出JSON。20ms Input优先级Dispatcher心跳反映消息间隔（不是绘制帧率），单调时钟记录各步骤耗时和实际托管线程，另记GC与分配量。

实际根因：MainViewModel.TickAsync 每次周期 PersistTimerAsync 后无条件 Refresh。SaveTimer已在后台线程，整页Refresh却在UI线程：清理/重建科目章节集合、重复读记录、重建Presentation/Analytics、重建日历并通知知识树摘要，然后触发布局与绘制。

修复前125秒：7次周期Refresh在UI线程，中位79.18ms、最长98.18ms；后台SaveTimer中位9.89ms、最长15.47ms；Tick异步墙钟最长113.26ms；心跳最大间隔177.12ms，7次超过100ms。不是单凭15秒参数推断。未发现另一项同周期备份/日志任务；GC记录不足以解释每次长任务，直接可追溯路径是UI刷新链。

按用户补充决策：后台检查点间隔仍为15秒，原事务、失败恢复和可信时间来源不改；相同Running状态的检查点不再整页Refresh。暂停、结束、自动完成、异常状态、日期变化以及明确数据操作更新视图。大数字继续每秒变化，页面说明暂停/结束后更新汇总；暂停状态立即反映到主/迷你，再做保存和汇总。

初步优化后125秒：周期Refresh=0（仅主动暂停时一次83.17ms），Tick最长21.86ms；后台SaveTimer中位9.70ms。整体心跳仍有121.79ms间隔，来自主动暂停汇总，不能宣称所有操作均<50ms。最终候选须再次采样并按原始结果报告，不用此初步数据冒充最终程序。

未修改SQLite、章节/知识包、毫秒聚合、跨日/未知间隙/休息语义；未增大检查点间隔；未添加后台查询队列或泛化并发框架。保留现有Busy串行保护，写入异常或锁等待不属于本轮周期正常路径的性能承诺。
